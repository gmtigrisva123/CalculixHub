# Admin and Arena

Apply `supabase/admin-arena-setup.sql` (safe to rerun) in this project's Supabase SQL Editor. It preserves existing rows and settings, and wraps the three new migrations in a transaction and seeds the 124 Learn questions without overwriting existing edits. It requires the existing CalculixHub profiles/attempts schema. No credentials are present in the SQL.

The local ignored `.env` contains server-only Admin configuration. Production must configure SUPABASE_SERVICE_ROLE_KEY, ADMIN_ACCESS_CODE_HASH and ADMIN_SESSION_SECRET on its backend too. Never use a VITE_ prefix for these values. The frontend cannot perform administrative operations on a static-only deployment.

Any signed-in Supabase account that enters the correct code becomes an administrator; no fixed owner email is used. The code is verified as a salted scrypt hash. Elevated HMAC sessions last 30 minutes, remain in component memory and are bound to account and settings version. Changing the code or revoking sessions invalidates other elevated sessions. Removing code entry permits already-approved administrators to return using their regular account; it does not open Admin to visitors. Code failures are throttled in-process; horizontally scaled production should replace the counter with a shared store.

Admin can create, publish, duplicate, close and permanently delete arenas; edit/archive numeric Learn questions; inspect/export match results; list up to 100 accounts; suspend or restore accounts; and inspect the latest 50 audit records. Archive preserves history. Arena questions are snapshots; started matches cannot have their questions, timing or duration rewritten. Titles/descriptions may change; closure remains available. Audit logging currently follows successful actions and is not a tamper-proof compliance ledger. Account deletion, arbitrary SQL/source editing and payments are intentionally not implemented.

Students use anon-key clients carrying their own authenticated JWT. Database RPCs enforce registration, opening times, deadlines, answer grading, attempt limits, forfeits and points. Direct access to Admin and Arena tables is denied. Practice grading also uses a constrained JWT RPC rather than the service-role key. Arenas do not award registration points. Each numeric question allows three submissions; a pass or three misses ends the question with no reward. Match solutions appear after finishing. Finished rankings use integer earned points. The schedule loads real database rows, with explicit setup/connection errors instead of fixture opponents.

IRT is Rasch 1PL EAP using an N(0,1) prior and 81 quadrature nodes. Only the first response to each item contributes; retries cannot improve theta. Posterior standard deviation is shown alongside theta. Difficulty values are editorial priors derived from the question rubric, not empirically calibrated parameters. Collect real response data and fit/validate item parameters, dimensionality and differential item functioning before treating these estimates as psychometric evidence. Points and IRT are separate measures. Reusing public Learn questions in a competitive arena makes their solutions discoverable; write fresh private match questions before using rankings for prizes or formal selection.

Validation: TypeScript checks, production build, PostgreSQL/PGlite migrations and authorization/grading tests. Run the suite serially on this machine: `npx vitest run --maxWorkers=1 --no-file-parallelism`. Browser checks cover the Arena lobby and signed-out Admin gate; signed-in hosted flows require applying the migration and a real learner session.
